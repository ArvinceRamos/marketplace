# Audit — 2026-10-13

Scope: security and money loopholes, logic edge cases, free-tier risks (Render / Vercel / Supabase),
and the UX of the profile and listing pages. DPA/BIR compliance is out of scope (personal project).

**Status (2026-10-14): fixed in Phase 14** except where noted below. Each fix has a test that
reproduces the problem (`backend/tests/integration/test_audit_fixes.py`). Decisions: paid meetups
are cancelled by the seller only, with a seller "buyer took the item" report; escalated disputes
refund the buyer after 14 days without a moderator.

Overall: identity comes only from the token, RLS is on every table, money moves only through
locked definer functions, the ledger is zero-sum and append-only, and webhooks are signed and
idempotent. The problems are in the rules between buyer and seller and in free-tier sizing.

## Findings (most severe first)

### A. Security and money loopholes
| # | Sev | Finding | Where | Fix idea |
|---|---|---|---|---|
| A1 | **High** (if demo tools are on when hosted) | **A seller can release escrow to themselves.** Online delivery order: the seller taps Ship, then "Advance tracking" ×4 until delivered, then "Skip ahead" (sets `confirm_by` to the past). The next read auto-completes the order and pays the seller. The buyer never gets the 2-day dispute window. Both demo tools only check "is a participant", not "is the buyer". | `demo_fast_forward` (700:384), `advance_tracking` (orders.py), `actions_for` | Only the buyer may fast-forward `confirm_by`. Only the buyer may push the final `delivered` step. Add a test for each. |
| A2 | **High** (logic) | **Buyer walk-away at a meetup.** On a paid meetup order the buyer can cancel any time in `confirmed` and get a full refund. A buyer can inspect the item, take it, keep the code, then cancel (or let `meet_by` run out). The seller has no dispute path; disputes are buyer-only. The seller's hint says "Ask for it after the buyer has checked the item", but it never says "keep the item until the code is accepted". | `order_cancel` (500), `handover-form.tsx` | 1) Change the copy: "Don't hand over the item until 'Complete handover' succeeds." 2) Optionally block buyer self-cancel of a paid meetup order within X hours of `meet_by`, or let the seller open a dispute. You decide. |
| A3 | Medium | **Free reservation squatting.** Cash-meetup and COD orders skip payment and are `confirmed` at once. The listing is then `reserved` for 7 days (meetup) or 5 days (ship-by) at zero cost. With `create_order` at 20/hour, one account can lock about 480 listings a day. Only the seller can undo it, by cancelling each order by hand. | `order_create` | Cap open unpaid (cash/COD) orders per buyer (e.g. 3). Shorten the hold for unpaid orders (e.g. 48 h). |
| A4 | Medium | **Fake reviews cost nothing.** Two accounts can run a cash-meetup order (no money moves), enter the code, and both leave 5 stars. Reviews unlock from any completed order. | `review_create` | Only count reviews from online orders in `rating_summary`, or label cash-order reviews. Rate-limit cash orders per buyer–seller pair. |
| A5 | Medium | **Bait-and-switch on listings.** Sellers can edit the title, description, condition and photos at any time, even while the listing is reserved. Orders save only the title, price and cover path. In a "not as described" dispute, the admin cannot see what the listing said at purchase time. Deleting a photo also removes the cover file the order points to. | `update_listing`, `remove_photo`, `orders` table | Block field edits and photo changes while `reserved`. Save `description` and `condition` on the order at creation. |
| A6 | Low–Med | **Restricted sellers can still edit live listings** (title, price, description, photos). The restriction only blocks create, publish and resume. | `update_listing`, `add_photos` | Call `ensure_not_restricted` in update and photo routes. |
| A7 | Low | **Admin can rule on their own dispute.** `admin_resolve_dispute` does not check that the admin is not the buyer or seller. | 700:405 | Refuse when `auth.uid()` is in (buyer, seller). |
| A8 | Low | **Account deletion race.** The open-order check runs, then photos are deleted, then the Auth user is deleted. If a buyer places an order in between, the DB trigger blocks the Auth delete (good). But the photos are already gone, so the active listing is left with no photos. | `safety.delete_account` | Before removing files, set the user's active listings to paused in the same transaction. |
| A9 | Low | Routes with no rate limit: `PATCH /me` (lets someone churn or squat usernames), `PATCH /listings/{id}`, favorites, offer accept/reject. | api/v1 | Add cheap per-user limits. |

**Things you asked about that hold up:**
- **Meetup codes are not brute-forceable.** 6 digits come from `gen_random_bytes`. Each code allows 5 tries, then it locks, and only the buyer can make a new one. The seller's chance of guessing is about 5 in 1,000,000 per code.
- **No unauthorized wallet refund path was found.** Refunds happen only through: cancel in an allowed state, timers, the seller refunding a dispute, or an admin. Withdrawals use an advisory lock and a balance check. Webhook amounts must match.
- **Listing edits are validated on the server.** Ownership comes from the token, the column list is fixed, `extra=forbid` is set, and triggers and RLS check again. The gaps are A5 and A6, not missing validation.
- **Account deletion during escrow is blocked.** It is refused while the user has open orders or a balance, at the API and again by a trigger.

### B. Logic edge cases
- **No disputes after a meetup.** This is by design: the order completes when the code is entered. A "post-meetup dispute" cannot happen. Document it and show it in the buyer UI ("Only give the code once you're happy").
- **Escalated disputes never time out.** If nobody runs `/admin`, the money stays held forever and **both users can never delete their accounts**. Add an admin-less fallback, for example a refund after 14 days escalated.
- **Cash and COD orders have no protection, but still unlock reviews.** See A4.
- **A dispute refund marks the item sold** (the buyer keeps it). This is a known design choice. Combined with A5, it is easy to abuse with "not as described".

### C. Free-tier risks
| # | Sev | Risk | Fix |
|---|---|---|---|
| C1 | **High** | **Out-of-memory on Render (512 MB).** `MAX_PIXELS` is 40 MP. A 40 MP PNG or WebP decodes to about 160 MB in RGBA. `_to_rgb` and `exif_transpose` make more copies, so one upload can peak around 400–450 MB. Two uploads at once, or one request with 8 photos (64 MB of raw bytes held in memory), can kill the instance. | Lower `MAX_PIXELS` to about 16 MP. Process one image at a time (an `asyncio.Semaphore(1)` around `process_image`). Resize in the browser to about 2000 px before upload (already listed as not built). |
| C2 | **High** | **The search rate limit is shared by every visitor once hosted.** Search pages render on Vercel, so the API sees Vercel's IP, not the visitor's. The `search` limit of 120/min per IP then covers all users together. Going over it returns 429, and the visitor sees the "server waking" error page. | Cache public lists in Next (`'use cache'` + `cacheLife`, since `cacheComponents` is on). Raise or remove the per-IP search limit for server-side calls. |
| C3 | Medium | **Nothing is cached.** `/categories`, `/locations`, home and search hit Render and Postgres on every page view. That costs Render bandwidth (5 GB) and keeps the API warm. | Use `'use cache'` with hours-long life for categories and locations, and about 60 s for search and home. |
| C4 | Low | **Listing page fetches the same listing twice for signed-in users** (once on the server, once in the client `ListingViewerPanel`). | Add a small `/listings/{id}/viewer` endpoint that returns only `is_owner`, the chat ID and the order ID. |
| C5 | Info | No feature is over-engineered enough to break a limit. Lazy timers, the in-memory limiter, the ledger and the mock providers are all cheap. Polling (30 s badge, 15 s open order, chat) only runs in visible tabs. The cost of the extra features is maintenance, not runtime. |

## D. UX review — profile and listing pages
**Listing page (`app/listing/[id]/page.tsx`, `listing-viewer-panel.tsx`)**
1. The CTA area is an empty 44 px box until the session check and a second API call finish. Buy and Chat pop in late, which is slow on a cold Render. Show the guest CTAs at once, then upgrade them.
2. Desktop gallery: every photo sits in a 2-column grid, so 8 photos make a very long page. There is no lightbox, zoom or thumbnail strip. The mobile swipe row has no "1 / 8" indicator.
3. The seller card has no rating or review count at the moment of decision, even though the profile has that data. It is the strongest trust signal you have.
4. On mobile, the description comes after the whole action panel, the specs, the seller card and the safety text.
5. After the listing, the page ends: no "More from this seller", similar items or share button.
6. The owner sees only Edit / My listings, with no quick Pause / Mark sold on the page.
7. The safety notice is a dense caption paragraph. Use a short line plus a link to /safety, or make it collapsible.

**Seller page (`app/seller/[username]/page.tsx`)**
1. Reviews sit below a paginated grid, so they are far down. Use Listings | Reviews tabs, or a review summary near the header.
2. Reviews are capped at 50 with no paging, and the list uses `key={i}`.
3. The header has no stats strip (items sold, rating, followers, joined) that can be scanned at a glance.

**Own profile (`app/profile/*`)**
1. **There is no way to upload an avatar.** The API has no endpoint and the UI has no control. Avatars exist only in demo data.
2. City can be set through the API, but the edit form has no field for it. The public page shows the city, so it is always empty for real users.
3. `/profile` is a bare data list and looks nothing like your public seller page. There is no "View public profile" link, no rating, and no listings preview. Suggest: make `/profile` your public page plus an owner toolbar.
4. Shortcuts to Orders, Wallet, Favorites and Settings are only in the header menu.
